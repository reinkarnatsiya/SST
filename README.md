# Практическая работа 1. Тестирование веб-приложения методом чёрного ящика

## Цель работы

Получить практические навыки тестирования программного продукта методом чёрного ящика:

* изучить функциональность приложения;
* определить основные функциональные области;
* разработать подробный чек-лист;
* разработать и выполнить тест-кейсы;
* применять техники тест-дизайна;
* выявлять и оформлять обнаруженные дефекты;
* фиксировать результаты тестирования в системе управления тестированием.

---

## Объект тестирования

Опубликованная версия программного продукта:

https://site-pizza.relaxdev.ru/

## Инструмент тестирования

Для создания, выполнения и хранения тестовой документации используется система управления тестированием [FireTMS](https://firetms.ru/).

Все результаты практической работы должны быть представлены в рабочем пространстве системы.

# Задание

Провести функциональное тестирование опубликованной версии программного продукта методом чёрного ящика.

Работа выполняется поэтапно:

1. Изучить программный продукт.
2. Определить основные функциональные области приложения.
3. Создать рабочее пространство в FireTMS.
4. Создать разделы для группировки тестовой документации.
5. Разработать **подробный чек-лист для всего приложения**.
6. На основе чек-листа разработать тест-кейсы.
7. Выполнить тест-кейсы и зафиксировать результаты.
8. При обнаружении дефектов оформить их в FireTMS.
9. Оценить полноту проведённого тестирования.

> **Важно:** тестирование выполняется методом чёрного ящика. Доступ к исходному коду приложения для выполнения работы не требуется.

# 1. Изучение программного продукта

Перед разработкой тестовой документации необходимо самостоятельно изучить опубликованную версию приложения.

В ходе изучения необходимо определить:

* основные функциональные возможности;
* функциональные области приложения;
* основные пользовательские сценарии;
* доступные действия пользователя;
* ограничения при вводе данных;
* состояния объектов системы;
* переходы между состояниями;
* зависимости между функциональными возможностями.

Необходимо самостоятельно определить, **что именно и каким образом следует проверять**.

Не следует ограничиваться только очевидными позитивными сценариями.

Структура рабочего пространства должна быть логичной и удобной для поиска тестовой документации.

# 3. Разработка подробного чек-листа

## Обязательный этап работы

После изучения приложения необходимо разработать **подробный чек-лист, охватывающий всё приложение**.

Чек-лист должен включать проверки всех основных функциональных областей, пользовательских сценариев и значимых вариантов поведения системы.

Например, если приложение содержит:

* авторизацию;
* регистрацию;
* каталог;
* поиск;
* корзину;
* оформление заказа;
* личный кабинет;

то чек-лист должен содержать проверки **по всем этим функциональным областям**, а не только по одной из них.

Чек-лист должен стать основой для последующей разработки тест-кейсов.

---

## Требования к чек-листу

Чек-лист должен содержать конкретные проверки, а не общие формулировки.

Плохо:

> Проверить авторизацию.

Хорошо:

> Проверить авторизацию с корректными учётными данными.

> Проверить авторизацию с пустым логином.

> Проверить авторизацию с пустым паролем.

> Проверить авторизацию с неверным паролем.

> Проверить авторизацию с несуществующим пользователем.

---

В зависимости от функциональности необходимо рассмотреть:

* основной позитивный сценарий;
* альтернативные сценарии;
* негативные сценарии;
* обязательность полей;
* корректные и некорректные данные;
* пустые значения;
* граничные значения;
* минимальные и максимальные значения;
* различные форматы данных;
* специальные символы;
* повторное выполнение действий;
* некорректные действия пользователя;
* различные состояния системы;
* переходы между состояниями;
* сохранение введённых данных;
* сообщения об ошибках;
* доступность элементов интерфейса;
* корректность переходов между страницами;
* другие проверки, которые имеют смысл для конкретной функциональности.

Чек-лист должен обеспечивать **максимально полное и рациональное покрытие всего приложения**.

При составлении чек-листа необходимо применять подходящие техники тест-дизайна.

Чек-лист необходимо разместить в рабочем пространстве FireTMS.

---

# 4. Применение техник тест-дизайна

При составлении чек-листа и последующих тест-кейсов необходимо использовать подходящие техники тест-дизайна.

Не требуется применять каждую технику к каждой функциональности. Необходимо самостоятельно определить, какие техники подходят для конкретной проверки.

## 4.1. Эквивалентное разбиение

Необходимо выделять классы входных данных, которые должны обрабатываться системой одинаковым образом.

Например:

* корректные значения;
* некорректные значения;
* пустое значение.

Не требуется проверять каждое возможное значение, если их поведение можно представить соответствующими классами эквивалентности.

---

## 4.2. Анализ граничных значений

Если функциональность содержит ограничения, необходимо проверить значения:

* ниже границы;
* на границе;
* выше границы.

Например, если поле допускает от 1 до 10 символов, необходимо рассмотреть:

* 0 символов;
* 1 символ;
* значение внутри диапазона;
* 10 символов;
* 11 символов.

Конкретные границы необходимо определить самостоятельно на основании поведения приложения.

---

## 4.3. Тестирование переходов состояний

Если объект системы имеет несколько состояний, необходимо проверять не только сами состояния, но и переходы между ними.

Например:

> Ожидает → Готовится → Готово → Выдан

Необходимо проверить:

* возможность перехода;
* корректность перехода;
* недопустимые переходы;
* поведение системы после перехода.

Техники тест-дизайна не требуется оформлять отдельным документом.

Их применение должно быть отражено непосредственно в чек-листе и тест-кейсах.

---

# 5. Разработка тест-кейсов

После составления чек-листа необходимо разработать тест-кейсы на его основе.

Необходимо разработать **не менее 10 тест-кейсов**.

Тест-кейсы должны обеспечивать хорошее покрытие функциональности приложения и не должны представлять собой набор однотипных проверок.

При разработке необходимо учитывать:

* позитивные сценарии;
* негативные сценарии;
* различные варианты входных данных;
* граничные значения;
* некорректные действия пользователя;
* различные состояния системы;
* переходы между состояниями;
* другие значимые варианты поведения.

При оформлении тест-кейсов необходимо использовать структуру и поля, представленные в примере тест-кейса в ветке `main` репозитория.

Тест-кейс должен быть:

* понятным;
* однозначным;
* воспроизводимым;
* логично сформулированным;
* достаточным для проверки соответствующего сценария.

---

# 6. Выполнение тест-кейсов

После разработки тест-кейсов необходимо выполнить их на опубликованной версии приложения.

Для каждого тест-кейса необходимо зафиксировать результат выполнения в FireTMS.

При выполнении теста необходимо сравнить:

* ожидаемый результат;
* фактический результат.

Если фактический результат соответствует ожидаемому, тест-кейс считается пройденным.

Если фактический результат отличается от ожидаемого, необходимо определить, является ли обнаруженное поведение дефектом.

Если в процессе выполнения тестирования обнаруживается новый значимый сценарий, необходимо при необходимости дополнить чек-лист и тестовую документацию.

---

# 7. Оформление дефектов

При обнаружении дефекта необходимо создать соответствующую запись в FireTMS.

Описание дефекта должно содержать информацию, необходимую для его воспроизведения.

При оформлении дефекта необходимо использовать структуру и поля, представленные в примере дефекта в ветке `main` репозитория.

В зависимости от доступных полей FireTMS необходимо указать:

* название дефекта;
* предусловия;
* тестовые данные;
* шаги воспроизведения;
* ожидаемый результат;
* фактический результат;
* приоритет;
* серьёзность;
* статус;
* доказательства обнаруженного дефекта.

### Пример

Плохо:

> Не работает корзина.

Хорошо:

> Товар не удаляется из корзины после нажатия кнопки «Удалить».

Дефект должен быть реальным, воспроизводимым и подтверждаться результатами тестирования.

---

# 8. Результат работы

В рабочем пространстве FireTMS должны находиться:

* логично организованные разделы;
* подробный чек-лист всего приложения;
* тест-кейсы, разработанные на основе чек-листа;
* результаты выполнения тест-кейсов;
* оформленные обнаруженные дефекты.

Отдельный письменный отчёт по результатам работы не требуется.

# 9. Критерии оценивания

## Оценка «3» — подробный чек-лист

Для получения оценки **«3»** необходимо:

* изучить приложение;

* создать рабочее пространство в FireTMS;
* создать логичную структуру разделов;
* разработать **подробный чек-лист всего приложения**;
* разместить чек-лист в FireTMS.

Чек-лист должен охватывать основные функциональные области и значимые сценарии приложения.

В нём должны присутствовать не только очевидные позитивные проверки, но и подходящие для конкретной функциональности:

* негативные сценарии;
* различные варианты входных данных;
* ограничения;
* граничные значения;
* некорректные действия;
* состояния системы;
* другие значимые проверки.

**Формальный чек-лист из нескольких общих пунктов не соответствует требованиям на оценку «3».**

## Оценка «4» — тест-кейсы и выполнение

Для получения оценки **«4»** необходимо выполнить все требования на оценку «3» и дополнительно:

* разработать не менее 10 тест-кейсов;
* разработать тест-кейсы на основе чек-листа;
* применить подходящие техники тест-дизайна;
* выполнить разработанные тест-кейсы;
* зафиксировать результаты выполнения в FireTMS;
* корректно определить статус проверок;
* оформить обнаруженные дефекты;
* обеспечить хорошее покрытие функциональности.

При оценивании учитывается **качество тест-кейсов и полнота проведённого тестирования**, а не только их количество.

10 хорошо продуманных тест-кейсов лучше, чем большое количество однотипных проверок.

## Оценка «5» — качественное и полное тестирование

Для получения оценки **«5»** необходимо выполнить все требования на оценку «4» и продемонстрировать высокий уровень самостоятельного тестирования.

Дополнительно оцениваются:

* максимально полное покрытие функциональности приложения;
* грамотное применение техник тест-дизайна;
* наличие позитивных и негативных сценариев;
* проверка граничных и некорректных значений там, где это необходимо;
* проверка альтернативных сценариев;
* проверка различных состояний системы;
* проверка переходов между состояниями;
* отсутствие очевидных пропусков в тестировании;
* качество и воспроизводимость тест-кейсов;
* корректность определения ожидаемого и фактического результата;
* **выявление всех обнаруженных в процессе качественного тестирования дефектов**;
* подробное и корректное оформление каждого обнаруженного дефекта;
* наличие доказательств дефектов;
* правильная оценка серьёзности и приоритета дефектов;
* способность дополнить проверки, если в ходе тестирования обнаруживается новый потенциально проблемный сценарий.

> **Важно:** количество найденных дефектов само по себе не определяет оценку. Не требуется искусственно искать или создавать большое количество дефектов. Для оценки «5» необходимо не пропустить дефекты, которые можно было обнаружить при качественном и достаточно полном выполнении разработанных проверок.

**Главный критерий оценки — качество тестирования, а не количество созданных тест-кейсов или найденных дефектов.**

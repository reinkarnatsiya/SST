# Практическая работа 1. Тестирование веб-приложения методом чёрного ящика

### Цель работы

Получить практические навыки тестирования программного продукта методом чёрного ящика, разработки и выполнения тест-кейсов, применения техник тест-дизайна и оформления обнаруженных дефектов.

### Объект тестирования

Опубликованная версия программного продукта: https://site-pizza.relaxdev.ru

### Инструмент тестирования

Для создания, выполнения и хранения тестовой документации используется система управления тестированием [**FireTMS**](https://firetms.ru).

Все результаты практической работы должны быть представлены в рабочем пространстве системы.

---

# Задание

Провести функциональное тестирование опубликованной версии программного продукта.

В процессе выполнения работы необходимо:

1. Изучить программный продукт.
2. Определить основные функциональные области приложения.
3. Создать рабочее пространство в FireTMS.
4. Создать разделы для группировки тест-кейсов.
5. Разработать и выполнить тест-кейсы, зафиксировать результаты выполнения в FireTMS.
6. При обнаружении дефектов оформить их в FireTMS.
7. Применить изученные техники тест-дизайна при разработке тест-кейсов.

> **Важно:** тестирование выполняется методом чёрного ящика. Доступ к исходному коду приложения для выполнения работы не требуется.

---

# 1. Изучение программного продукта

Перед разработкой тест-кейсов необходимо самостоятельно изучить опубликованную версию приложения.

В ходе изучения необходимо определить:

- основные функциональные возможности;
- функциональные области приложения;
- основные пользовательские сценарии;
- доступные действия пользователя;
- ограничения при вводе данных;
- состояния объектов системы;
- различия в возможностях обычного пользователя и администратора.

---

# 2. Создание рабочего пространства в FireTMS

Создать рабочее пространство для тестирования программного продукта.

В рабочем пространстве создать разделы, соответствующие функциональным областям приложения.

Тест-кейсы необходимо распределить по соответствующим разделам.

Структура рабочего пространства должна быть логичной и удобной для поиска тестовой документации.

---

# 3. Разработка тест-кейсов

Необходимо разработать не менее **10 тест-кейсов**.

Тест-кейсы должны обеспечивать максимально полное и рациональное покрытие функциональности приложения.

При разработке тест-кейсов необходимо учитывать:

- позитивные сценарии;
- негативные сценарии;
- различные варианты входных данных;
- граничные значения;
- некорректные действия пользователя;
- различные состояния системы;
- переходы между состояниями.

При оформлении тест-кейсов необходимо использовать структуру и поля, представленные в примере тест-кейса в ветке `main` репозитория.

Тест-кейс должен быть понятным и воспроизводимым другим тестировщиком.

---

# 4. Применение техник тест-дизайна

При разработке тест-кейсов необходимо применять изученные техники тест-дизайна.

В работе необходимо использовать:

При разработке тест-кейсов необходимо применять изученные техники тест-дизайна.

## 4.1. Эквивалентное разбиение

Необходимо выделять классы входных данных, которые должны обрабатываться системой одинаковым образом.

Например, для некоторого поля можно выделить:

- корректные значения;
- некорректные значения;
- пустое значение.

Не требуется проверять все возможные значения, если их можно представить соответствующими классами эквивалентности.

---

## 4.2. Анализ граничных значений

Необходимо проверять значения около границ допустимого диапазона.

В зависимости от конкретной функциональности могут использоваться:

- значение меньше границы;
- значение на границе;
- значение больше границы.

Граничные значения необходимо определять самостоятельно на основании поведения и ограничений приложения.

---

## 4.3. Тестирование переходов состояний

Необходимо учитывать изменения состояния объектов системы и проверять допустимые и недопустимые переходы между состояниями.

Например, для заказа может использоваться последовательность:

**Ожидает → Готовится → Готово → Выдан**

Необходимо проверить не только отдельные состояния, но и корректность переходов между ними.
Техники тест-дизайна не требуется оформлять отдельным документом. Их применение должно быть отражено непосредственно в тест-кейсах.

---

# 5. Выполнение тест-кейсов

После разработки тест-кейсов необходимо выполнить их на опубликованной версии приложения.

Для каждого тест-кейса необходимо зафиксировать результат выполнения в FireTMS.

При выполнении теста необходимо сравнить:

- ожидаемый результат;
- фактический результат.

Если фактический результат соответствует ожидаемому, тест-кейс считается пройденным.

Если фактический результат отличается от ожидаемого, необходимо определить, является ли обнаруженное поведение дефектом.

---

# 6. Оформление дефектов

При обнаружении дефекта необходимо создать соответствующую запись в FireTMS.

При оформлении дефекта необходимо использовать структуру и поля, представленные в примере дефекта в ветке `main` репозитория.

Описание дефекта должно содержать информацию, необходимую для его воспроизведения.

В зависимости от доступных полей FireTMS необходимо указать:

- название дефекта;
- фактический результат;
- шаги воспроизведения;
- ожидаемый результат;
- необходимые условия и тестовые данные;
- приоритет;
- серьёзность;
- статус;
- доказательства обнаруженного дефекта.

### Пример названия дефекта

**Плохо:**

> Не работает корзина

**Хорошо:**

> Товар не удаляется из корзины после нажатия кнопки «Удалить»

---

# 7. Дополнительное задание — чек-лист

Создание чек-листа является дополнительным заданием.

За качественно выполненный чек-лист можно получить **+1 балл**.

Необходимо:

1. Выбрать одну функциональную область приложения.
2. Составить чек-лист проверок.
3. Разместить чек-лист в рабочем пространстве FireTMS.

При оформлении чек-листа необходимо использовать структуру и содержание, представленные в примере чек-листа в ветке `main` репозитория.

Чек-лист должен содержать логичный набор кратких проверок.

> **Важно:** чек-лист не заменяет тест-кейсы и не входит в обязательные 30 тест-кейсов.

---

# 8. Результат работы

В рабочем пространстве FireTMS должны находиться:

- логично организованные разделы;
- не менее **10 тест-кейсов** с результатами выполнения;
- оформленные обнаруженные дефекты;
- чек-лист — при выполнении дополнительного задания.

Отдельный письменный отчёт по результатам работы **не требуется**.

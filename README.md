# Практическая работа 1. Тестирование веб-приложения методом чёрного ящика

## 1. Цель работы

Научиться проводить функциональное тестирование веб-приложения методом чёрного ящика:

* анализировать требования к системе;
* определять функциональные области приложения;
* составлять чек-лист проверок;
* разрабатывать тест-кейсы на основании чек-листа;
* выполнять тестирование;
* выявлять и описывать дефекты.

---

## 2. Объект тестирования

В качестве объекта тестирования используется веб-приложение **CRM Door** — система для управления производством и продажей дверей.

**Адрес приложения:**
https://crmdoor.ru/

В рамках работы используется демонстрационная версия приложения.

---

## 3. Инструмент для оформления результатов

Для создания и хранения тест-кейсов используется система **FireTMS**.

https://firetms.ru/

В FireTMS необходимо создать рабочее пространство для данной практической работы и использовать его для оформления результатов тестирования.

---

## 4. Задание

Необходимо провести функциональное тестирование веб-приложения CRM Door на основании технического задания.

Работа выполняется в следующей последовательности:

**Техническое задание → изучение приложения → чек-лист → тест-кейсы → выполнение тестов → фиксация дефектов.**

Главный результат работы — **качественный чек-лист и составленные на его основе тест-кейсы**.

Количество проверок само по себе не является показателем качества работы. Важно обеспечить разумное покрытие требований, не допускать необоснованных повторов и формулировать проверки так, чтобы другой человек мог однозначно понять, что именно необходимо проверить.

---

# 5. Изучение приложения

Перед началом тестирования необходимо изучить:

1. техническое задание на систему;
2. назначение приложения;
3. основные функциональные возможности;
4. роли пользователей;
5. жизненный цикл заказа;
6. основные объекты системы;
7. ограничения и правила работы системы.

При изучении приложения необходимо не просто просматривать страницы, а сопоставлять фактическое поведение системы с требованиями технического задания.

---

# 6. Роли пользователей

В CRM Door предусмотрено несколько ролей пользователей.

| Роль                       | Назначение                                        |
| -------------------------- | ------------------------------------------------- |
| Системный администратор    | Управление системой и её настройками              |
| Администратор компании     | Управление данными и настройками компании         |
| Руководитель отдела продаж | Управление продажами и контроль работы менеджеров |
| Менеджер                   | Работа с клиентами и заказами                     |
| Руководитель производства  | Управление производственным процессом             |
| Работник участка           | Выполнение производственных операций              |
| Снабжение                  | Работа с материалами и обеспечением производства  |
| Дилер                      | Работа с заказами в рамках предоставленных прав   |

При составлении проверок необходимо учитывать, что разные пользователи могут иметь разные права доступа.

Например, необходимо проверять не только возможность выполнить действие, но и **имеет ли конкретная роль право на его выполнение**.

---

# 7. Разработка чек-листа

## 7.1. Чек-лист — первый основной результат работы

До разработки подробных тест-кейсов необходимо составить **чек-лист функциональных проверок**.

Чек-лист должен быть создан на основании:

* требований технического задания;
* функциональных возможностей приложения;
* ролей пользователей;
* бизнес-логики системы.

Не следует начинать работу с написания большого количества тест-кейсов. Сначала необходимо определить, **что именно необходимо проверить**.

### Последовательность работы

1. Изучить техническое задание.
2. Изучить приложение.
3. Выделить функциональные области.
4. Определить, какие проверки необходимо выполнить.
5. Сгруппировать проверки по функциональным областям.
6. Оформить получившиеся проверки в виде чек-листа.
7. После этого выбрать проверки, которые необходимо подробно описать в виде тест-кейсов.

---

## 7.2. Что необходимо учитывать при составлении чек-листа

В зависимости от функциональности конкретного раздела следует предусмотреть:

* позитивные сценарии;
* негативные сценарии;
* корректные и некорректные данные;
* обязательные и необязательные поля;
* различные роли пользователей;
* права доступа;
* различные состояния объектов;
* переходы между состояниями;
* корректность отображения результатов операций;
* обработку ошибок;
* граничные значения там, где они применимы.

Чек-лист должен охватывать **существенные требования системы**, а не только проверять наличие кнопок и элементов интерфейса.

---

## 7.3. Требования к качеству чек-листа

Хороший чек-лист должен:

* соответствовать требованиям технического задания;
* охватывать основные функциональные области;
* содержать конкретные и проверяемые пункты;
* быть логично структурирован;
* учитывать положительные и отрицательные сценарии;
* учитывать различные роли пользователей;
* не содержать большого количества дублирующих проверок;
* позволять другому тестировщику понять, что именно необходимо проверить.

**Количество пунктов не является главным критерием.**

Например, чек-лист из 15 хорошо продуманных проверок может быть значительно лучше чек-листа из 50 формальных и повторяющихся пунктов.

---

# 8. Разработка тест-кейсов

Тест-кейсы создаются **после разработки чек-листа**.

Чек-лист отвечает на вопрос:

> **Что необходимо проверить?**

Тест-кейс подробно описывает:

> **Как именно выполнить проверку и какой результат должен быть получен?**

Для разработки тест-кейсов необходимо выбрать наиболее важные и показательные проверки из собственного чек-листа.

Тест-кейс должен содержать:

* название;
* предусловия;
* тестовые данные;
* последовательность действий;
* ожидаемый результат.

При необходимости могут быть указаны дополнительные поля: приоритет, постусловия, фактический результат и статус выполнения.

---

## 8.1. Пример тест-кейса

**Проверяемая область:** авторизация пользователя.

**Название:** Авторизация с неверным паролем.

**Предусловие:** пользователь находится на странице авторизации.

**Шаги:**

1. Ввести существующий логин.
2. Ввести неверный пароль.
3. Нажать кнопку «Войти».

**Ожидаемый результат:**

Пользователь не авторизуется в системе. На странице отображается сообщение об ошибке авторизации.

---

## 8.2. Требования к тест-кейсам

Тест-кейс должен быть:

* понятным;
* однозначным;
* воспроизводимым;
* связанным с конкретной проверкой из чек-листа;
* содержащим ожидаемый результат.

Другой тестировщик должен иметь возможность выполнить тест-кейс, не обращаясь к его автору за дополнительными объяснениями.

**Количество тест-кейсов не является главным критерием оценки.**

Гораздо важнее, чтобы выбранные тест-кейсы действительно проверяли значимые функции системы и позволяли получить достоверный результат.

---

# 9. Выполнение тестирования

После создания тест-кейсов необходимо выполнить их в демонстрационной версии CRM Door.

Для каждого тест-кейса необходимо зафиксировать фактический результат и определить статус:

* **Пройден** — ожидаемый результат получен;
* **Не пройден** — фактический результат отличается от ожидаемого;
* **Блокер** — выполнение невозможно из-за другой проблемы.

При обнаружении несоответствия требованиям необходимо создать дефект.

---

# 10. Регистрация дефектов

Обнаруженные дефекты необходимо оформить в FireTMS.

Описание дефекта должно позволять другому человеку воспроизвести проблему.

Рекомендуемая структура:

### Заголовок

Кратко описать проблему.

### Предусловия

Указать необходимые условия для воспроизведения.

### Шаги воспроизведения

Указать последовательность действий.

### Фактический результат

Что произошло в действительности.

### Ожидаемый результат

Что должно было произойти согласно техническому заданию.

При описании дефекта необходимо опираться на **наблюдаемое поведение системы и требования технического задания**, а не на предположения о причине ошибки.

---

# 11. Результат работы

В результате выполнения практической работы студент должен подготовить:

1. рабочее пространство в FireTMS;
2. чек-лист функциональных проверок CRM Door;
3. набор тест-кейсов, разработанных на основании чек-листа;
4. результаты выполнения тест-кейсов;
5. описания обнаруженных дефектов.

---

**Количество чек-листов, пунктов или тест-кейсов само по себе не определяет оценку.**

Основной критерий — **насколько грамотно студент определил, что необходимо проверить, насколько хорошо эти проверки покрывают требования и насколько качественно они оформлены**.
